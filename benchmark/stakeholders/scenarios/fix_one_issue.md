# Scenario: Fix One Issue（修一个问题）

> 覆盖产品树叶子：修复建议清单 → 改材料 → 依据确认。检验"报告不是只读的，能变成改的动作"。

## USER GOAL

报告里指出一个问题后，我想知道"具体改哪句话、怎么改"，改完后系统认得出来（状态变化或计数变化），而不是让我猜。

## STARTING STATE

- 已完成一次检查（见 `first_review.md`），报告页可见，至少有 1 条"待看/待改"的问题（可以是"当前范围尚未发现引用""待核对问题"或等价表述）。
- 材料源文件在手边可编辑（场外改 Markdown 即可，不要求在产品内嵌编辑器改）。
- tester 知道自己要改哪句话（例如补一句缺失的依据句），但 scenario 不给 oracle（改得对不对由 tester 自己的材料知识判断）。

## TASK

1. 在报告里选 1 个最像"会扣分"的问题，点回原文确认它说得对不对。
2. 找到系统给的改法建议（如果有），抄下原话（一字不改，用于核查过度断言）。
3. 场外改材料（只改这一处，别处不动），回到产品。
4. 按产品指引让它"知道我改了"（可能是重新上传、保存、再跑一次检查——只走 UI 给的路）。
5. 回到报告，判断：刚才那条问题状态变了吗？你分得清"变了/没变"吗？

## ALLOWED KNOWLEDGE

- 允许：自己的材料改了哪行、报告原话、产品 UI 上的按钮文字。
- 禁止：内部 API / 数据库 / 版本锚定实现 / Binding / Finding / SourceRef / 代码路径 / "后台应该怎么比"。只看 UI 告诉你什么。

## SUCCESS CONDITION

- [ ] 能说出"问题是XX要求、对应原文第X段、改法是补/改Y"（一句话动作，非空话）。
- [ ] 改法建议是具体动作（补哪类句子/改哪个数字/加什么限定），而不是"完善表述/优化逻辑"。
- [ ] 改后产品有可见反馈（状态/计数/文字变化，或明确说"暂无变化"），tester 能复述出来。
- [ ] 全程点回原文可用（改前改后各点一次）。

## BLOCKED CONDITION

- 报告里的问题点不回原文 → 无法确认真假 → BLOCKED。
- 改完后找不到"让它重看"的入口；或入口点了无反馈。
- 建议页是空话拼盘（"请完善"×3，无具体指向）→ 记 DEAD_END（"不知道改哪"）。
- 任何一步需 API/数据库/源码绕过 → 直接 BLOCKED，本轮作废。

## TRUST FAILURE

- 建议里出现禁用词：已满足/已支撑/覆盖率%/分数/"改完包过"。
- 明明没改（或改错地方）却显示"已解决/已满足"。
- 建议与材料无关还很肯定（例如让论文补 baseline，但材料根本不是论文且无此要求）。
- 改前改后状态混乱：旧结论冒充新结论且无版本区分。

## METRICS

- `USEFUL_MOMENTS`（主）：改法建议有几条是真可执行的。
- `BLOCKED_FLOWS`：改→反馈链路卡住几次。
- `TRUST_FAILURES`：过度承诺/张冠李戴计数。
- `TIME_TO_FIRST_VALUE`：从打开报告到找到第一个可改动作的时长。
- `DEAD_ENDS`：看了报告仍不知道改哪的次数。
- `INTERNAL_CONCEPT_LEAKS` / `WAIT_WITHOUT_VALUE` / `DELIGHT_MOMENTS`：按 metrics.md 通用记法。

## 推荐 persona 组合

- 主力：`contestant`（"今晚改哪三行"视角）。
- 对抗：`adversarial_skeptic`（S2 矛盾数字改一处看系统跟不跟）。
- 抽查：`paper_author_reviewer`（措辞类修改："把'证明'改成'在X条件下观察到'"）。
