# Scenario: Create Revision（创建新版本）

> 覆盖产品树叶子：版本锚定（用户侧表现为"改完有个 v2"）。检验"改了不丢、旧结论不冒充新结论"。

## USER GOAL

我改完材料后，想留一个新版本（v2），旧的检查结果不丢失、不混淆，下次打开我分得清"这是哪一版、按哪个要求查的"。

## STARTING STATE

- 已有 1 份材料 + 1 次检查结果（报告可见）。
- 已在场外改好材料（1 处实质修改：补依据句 / 改数字 / 收敛措辞三选一）。
- 产品首页/材料页可见（不指定路由，只要求"人找得到回去的路"）。

## TASK

1. 找到"保存/创建新版本/再跑一次"类入口（按 UI 实际文字走，不猜内部词），把改后的材料交上去。
2. 确认新版本建好了：能说出"现在是第几版、上一版还在不在"。
3. 对新版本发起（或确认已发起）一次检查。
4. 对比记忆：说出"旧报告还在吗？标的是哪一版、哪个要求版本吗？"
5. 记录全程有无版本混淆（旧结论出现在新版本下且无标注）。

## ALLOWED KNOWLEDGE

- 允许：版本的大众含义（v1/v2/最新/历史）、要求版本（rev N 的大众含义）、自己的修改内容。
- 禁止：revision 锚定实现 / rubric_id / 表 / API / commit / 代码路径。UI 没说"rev"就不要自己脑补 rev。

## SUCCESS CONDITION

- [ ] 新版本创建成功且可见（"v2/最新"或等价表述），旧版本可回看（或明确告知只保留最新，但提前说了）。
- [ ] 新旧报告分得清（版本号/时间/要求版本三者至少其二可见）。
- [ ] 新版本检查可发起且有反馈（进度/完成/失败话术三选一，不悬空）。
- [ ] 全程无"旧结论冒充新结论"（旧报告的结论原样出现在新版本下且无版本标注 → 不算成功）。

## BLOCKED CONDITION

- 找不到创建新版本的入口；入口点了无反馈；新版本建好但打不开。
- 新版本检查无法发起；或发起后 > 90 秒无话术。
- 版本列表与报告对不上（点 v2 进 v1 的内容）→ BLOCKED（数据错乱比没有更严重）。
- 需 API/数据库绕过 → BLOCKED，本轮作废。

## TRUST FAILURE

- 版本无标注却给结论（"已确认 N 条"但不说是哪一版的）。
- 旧结论在新版本下原样展示且无"待重跑/未评估"提示（版本混淆，致命）。
- 出现禁用词：已满足/已支撑/覆盖率%/分数/✅❌（版本场景下同样禁用）。
- 内部词裸奔：revision / rubric_id / hash / commit 直接甩给用户且无解释 → 先记 INTERNAL_CONCEPT_LEAK，伴随结论混淆则升级为 TRUST FAILURE。

## METRICS

- `BLOCKED_FLOWS`（主）：版本链路卡住几次。
- `TRUST_FAILURES`：版本混淆/无标注结论计数（一票否决级）。
- `SETUP_STEPS`：从报告页到新版本检查跑起来共几步。
- `WAIT_WITHOUT_VALUE`：等待无话术时长。
- `INTERNAL_CONCEPT_LEAKS` / `USEFUL_MOMENTS`（版本分得清即有用）/ `DEAD_ENDS`：通用记法。

## 推荐 persona 组合

- 主力：`enterprise_reviewer`（版本+范围签字视角）、`contestant`（"改完有没有 v2"视角）。
- 对抗：`adversarial_skeptic` S4（换要求版本后看旧结论是否标版本）。
