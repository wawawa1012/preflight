# Scenario S2-2: progressive_evidence（逐条出结果，不互相遮挡）

> Sprint 2 待执行资产（不改产品）。检验：一份清单至少 5 条要求时，结果是不是逐条出现；前三条完成后后面还继续；一个失败不遮挡其他条。

## USER GOAL

我用一份至少 5 条要求的清单查材料，我想看到结果一条一条出来（先出的先看），而不是等全部跑完才开奖；其中一条失败了，其他条不受影响。

## STARTING STATE（用户可见）

- 有一段新鲜手写的原始要求（≥5 条，每条一句话；用 `benchmark/uat/fixtures/raw_requirements_snippet.md` 作格式参考，但每次重写内容）。
- 有一份新鲜手写的 1 页材料（≤50 行）。
- 已建好一场 Review 并选好这份清单（按 Sprint 1 旅程走完"建 Review + 加材料"，本 scenario 从"发起检查"开始计时）。

## TASK（黑盒步骤）

1. 发起一次检查，开始掐表（t0）。
2. 记录：第一条结果出现的时间（t1），抄下它的原话 + 点回原文验证。
3. 继续看：前三条出完后，剩余条目是否继续（还是卡住/消失/要手动刷新）。
4. 记录：全部出完的时间（t2）；如有失败项，抄下失败话术原话，并检查其他条是否照常可看、可点。
5. 回答：一个失败是否遮挡了其他项？（"其他项看不了/点不回去/被失败提示盖住" = 遮挡。）

## ALLOWED KNOWLEDGE

- 允许：清单 5 条原文、材料内容、"第 X 条/正在查/已出/失败/重试"等 UI 状态词。
- 禁止：并发/队列/request/超时实现、API、DB、代码路径、oracle。只看 UI 是否逐条呈现。

## SUCCESS CONDITION

- [ ] 第一项结果可计时出现（t1 可记录），且点得回原文。
- [ ] 前三项出完后剩余项继续执行，无需 tester 手动刷新/重进（自动继续或有明确"继续"按钮且一点就继续）。
- [ ] 全部完成时间 t2 可记录；失败项（如有）话术诚实（"这条没跑出来，其他条可先看"或等价表述），失败不遮挡其他项（其他项照常可看、可点）。
- [ ] 每条结果标得出处（点回原文）或诚实标注"未评估/当前范围尚未发现引用（+范围）"。

## BLOCKED CONDITION

- 发起后 > 90 秒无任何一条结果且无进度话术。
- 前三条出完后续无动静且无"继续/重试"指引（ progressive 中断）。
- 失败项盖住整页（其他结果看不了）且无关闭/绕行。
- 需 API/刷新网络面板/读源码推进 → BLOCKED，本轮作废。

## TRUST FAILURE

- 用"全部通过/覆盖率%/分数"总结渐进过程（过程没跑完就下整卷结论）。
- 失败项被藏起来（无提示）但计数照涨；或失败项显示为"已确认/已满足"。
- 结果与条目错位（第 3 条的结论点回第 5 条的原文，张冠李戴）。
- "本次未再检出/无问题"类话术缺三件套（搜了哪几条？为什么？点哪看？）。

## METRICS（本 scenario 必记三段时间）

- `TIME_TO_FIRST_VALUE` = t1 - t0（第一项出现时间，主指标）。
- 全部完成时间 t2 - t0（记在 `WAIT_WITHOUT_VALUE` 证据栏 + 行为流）。
- `BLOCKED_FLOWS`：渐进中断/失败遮挡次数。
- `TRUST_FAILURES`：错位/藏失败/提前下整卷结论计数。
- `SETUP_STEPS`（从发起检查计）/ `DEAD_ENDS`（等半天不知道还要不要等）/ `INTERNAL_CONCEPT_LEAKS`（并发/队列/request 裸奔）/ `WAIT_WITHOUT_VALUE`（无话术等待秒数）/ `USEFUL_MOMENTS`（逐条点得回去的条数）/ `DELIGHT_MOMENTS`（逐条出现+进度诚实则记）。

## 推荐 persona

- 主力：`contestant`（"先改前三条，后面的还来不来"）、`enterprise_reviewer`（逐条追溯）。
- 对抗：`adversarial_skeptic`（把 1 条写成必失败的陷阱材料，看它遮不遮挡其他条）。
