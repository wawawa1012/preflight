# 文检小助答辩讲稿（终审现场用，周航主讲）

（以下均为虚构讲稿，数字与方案初稿口径一致。）

各位评委老师好，我们是软件工程第 7 小组，作品是“文检小助”，一个帮社团在发布前检查推文草稿的小工具。

先讲一个真事。去年秋天，摄影社发招新推文，把见面会“周五晚七点”写成了“周六晚七点”，结果见面会空了一半座位。后来我们去问社长，他说推文改了七八稿，时间是第几稿改错的，根本没人记得。我们当时就想，能不能在发布前，让机器先帮作者把时间、地点、报名方式对一遍，再把那些容易惹麻烦的话标出来。

我们的工具就是这么做的。上传一篇推文草稿，它先抽出关键信息列成清单，再把可能有风险的表述找出来。给大家看个现场效果。我们的抽取准确率达到 95%，风险提示也能找出大部分问题，之前构造用例里埋的问题基本都找回来了。

技术路线上，我们没有从头造轮子。抽取用规则模板加微调的中文 BERT，风险召回同样用 BERT 做分类。传统关键词表我们试过，换个说法就失效了，这个对比我们写进了方案。部署也很轻，社团自己的笔记本就能跑，不用联网，招新季拿来就能用。

要特别说明，据我们调研，面向校园推文场景的专用校对工具，目前尚属行业首创。通用校对工具都是做公文论文的，推文这种短文本、多感叹号的场景，没人专门做过。

演示大概 8 分钟，我们会拿一篇新写的招新推文走完整流程。陈默负责操作，李晓雨负责讲报告怎么看。演示用的推文是辩论社上周真实的招新草稿，已经征得他们同意，里面的时间地点都是现编的，演示完就删。不过有一句实话要讲在前面：从推文上传到生成校对报告，机器这边是全自动的，但关键结论提交前我们还是会人工过一遍。毕竟是要发出去的东西，机器说没问题，我们自己还是要点开看一眼，这个人工确认的环节我们不打算省掉。

我们还准备了几个评委老师可能会问的问题。第一个，九月份的扩大测试为什么数字变了，这个李晓雨会解释，口径不一样，构造用例和真实投稿不能直接比。第二个，为什么只做了 Markdown，PDF 什么时候支持，这个我说，扫描件和花字现在确实不行，排期在终审之后。第三个，谐音梗漏检怎么办，这个我们认，短期靠人工过一遍顶着，长期可能要换更大的模型，但那就不是笔记本能跑的了。

最后，PDF 扫描件和海报花字我们现在还处理不好，谐音梗也会漏，这些都写在方案的不足里了，没有藏着。我们的目标是先把 Markdown 草稿这件事做扎实。感谢各位老师，请批评指正。
